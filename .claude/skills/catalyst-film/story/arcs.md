# Story arcs — shapes, not templates

An arc is the **shape of the argument**, not a form to fill in. Pick the shape your material already has, then let
the script bend it: stages can merge, swap, shrink to one line, or vanish into the visuals. A good arc is
invisible. The viewer should feel the story, not notice its stages.

## 1. Let the material choose (ask before picking)
| Question about the brief | If yes, the shape leans toward |
|---|---|
| Is there a **pain the viewer already feels** (cost, slowness, risk)? | **Problem → Solution** |
| Is it **new**, and is the mystery more interesting than the explanation? | **Launch teaser** |
| Is the product **its own best argument**, so watching it work convinces faster than talking? | **Demo-first** |
| Is there a **real use case** (an app, a team, a workflow) with a clear before and after? | **Customer story** |
| Is the point a **belief or a stance** (pricing philosophy, openness, the agent era)? | **Manifesto** |
| Does the message need **two moves**, such as a pain that turns out to be a belief? | **Blend**: see §4 |

If two shapes fit equally, choose the one **least like the last film in the series** (see §5).

## 2. The library
Stages in *italics* are optional: keep them only if the material earns them.

### A. Problem → Solution — *"you have this pain, here's the fix"*
`Problem → Stakes → Solution → How → Payoff`
- **Best for:** cost, time or complexity pain (CloudScale 2, Slate 30s).
- **Visual arc:** the *same* world, broken and then resolving. Broken means disorder, stillness and dim light; it is never a colour change.
- **Music:** tension (a minor pad, sparse pulse) → release on the solution → groove → resolve.
- **Watch out:** a stakes line that exaggerates. Dramatised numbers are flagged as "illustrative".

### B. Launch teaser — *"something new is here"*
`Glimpse → *Build* → Reveal → One feature → Name / date`
- **Best for:** new services, versions and events, when there's little to explain yet.
- **Visual arc:**
  - It starts with **fragments**: a close-up of one light carrier or one edge, or a silhouette in the void (L13, L7).
  - Each beat pulls the camera back and shows more.
  - The reveal is the full composition. Hold it.
- **VO:** sparse, or none until the reveal. Short sentences, second person ("You've been waiting…" is banned as a cliché; say something specific).
- **Music:** it rises the whole way. No groove until the reveal, then one hit on the name.
- **Layouts:** close-ups → a wide reveal → giant type for the name (L13 → L7 → L3 → L4).

### C. Demo-first — *"watch"*
`Action (cold open) → Result → *Second action* → Why it matters → CTA`
- **Best for:** developer tools, CLIs and agent workflows: anything that is impressive in real time.
- **Visual arc:**
  - Open **mid-action** with Type 2: a command already typing, a prompt already sent.
  - The result lands as a Type 1 system reaction.
  - The "why" comes *after* the viewer has seen it work. It's one line, with a reprise of the result.
- **VO:** narrates what we're seeing, in the present tense ("One prompt. It's live."). There's no setup line.
- **Music:** starts already in the groove, with no intro.
- **Layouts:** full-frame UI or window-in-world first, then a wide system shot, then a short CTA (full-UI → L10 → L5 → L4).

### D. Customer story — *"here's what happened when…"*
`Before → Turning point → After → Proof → CTA`
- **Best for:** use cases such as the ticket-booking flow, a team shipping faster, a student project going live.
- **Visual arc:** **one concrete thing** travels through the whole film (a booking, an app, a team's deploy). Before shows it struggling. After shows the same thing flowing.
- **Proof:** one real figure from the site (free-tier numbers, the components used), or one visible outcome. Never invent customer names, logos or quotes. If there is no real customer, frame it as "an app like yours".
- **Music:** warm and steady. A lift at the turning point.
- **Layouts:** lower third or panorama (L6 / L5) for the narrative, plus one big number for the proof (L12).

### E. Manifesto — *"what we believe"*
`Belief → Proof 1 → Proof 2 → *Proof 3* → Restated belief → CTA`
- **Best for:** pricing philosophy ("Pay for what you ship"), openness ("any framework, any agent"), the agent era.
- **Visual arc:**
  - The belief is **giant type** (L4 / L12).
  - Each proof is a small, fast Type 1 or Type 2 vignette: a triptych (L11), or quick cuts with the same verb family.
  - The restated belief returns to the opening type, now with the world built under it.
- **VO:** declarative and rhythmic, with parallel sentences ("Free bandwidth. Free collaborators. Free to grow.").
- **Music:** a confident groove from the start, with a hit on each proof.

## 3. Making it organic (the rules that matter more than the shapes)
1. **Write the script first, then name the arc.** Draft the VO as a story, then check which shape it has. Don't fill stages in order.
2. **"But / therefore", never "and then".** Each beat must connect to the next with *but* (a turn) or *therefore* (a consequence). If two beats only join with *and then*, merge them or cut one.
3. **No stage is mandatory except two:** the core idea must land, and the film must end on one clear action or name. Everything else can compress to one line, one image or nothing.
   - "Stakes" can be a single number on screen.
   - "How" can be one mechanism.
   - A solution can be told entirely in the visuals.
4. **Durations come from the script, not from percentages.** Give each beat what its words and its visual need (word budget + ≥ 1.0s per visual idea). The shares in `story-and-script.md` are a sanity check, not a target.
5. **Never announce the structure.** No "the problem:", no "here's how it works", no "introducing…". Let the turn happen in the picture.
6. **The visual arc carries the story arc.** The same world, metaphor or object changes state across the film (broken → whole, fragment → reveal, still → flowing). If the visuals could be shuffled without losing meaning, the arc isn't working.
7. **The ending answers the opening.** The last scene should rhyme with the first: the same spike now free, the same fragment now whole, the same belief now proven.
8. **Read it aloud without the visuals.** It should still make sense, with no beat feeling like a slide title.

## 4. Blends (when one shape isn't enough)
| Blend | Shape | Example |
|---|---|---|
| Problem → Manifesto | Pain, then "we think it shouldn't be this way", then proofs | Slate pricing: "Traffic spikes shouldn't come with an invoice." |
| Teaser → Demo | Fragments, a reveal, then watch it work | A new Catalyst service launch |
| Customer → Problem | Open on the "before" of one app, generalise the pain, then solve it | The ticket-booking flow |
| Demo → Manifesto | Cold-open action, then "this is how it should feel", then the belief | Agent-era messaging |

Keep a blend to **two shapes at most**. Three is a montage.

## 5. Series hygiene
- **Don't use the same arc in two consecutive films for the same audience.** Record the arc in each brief's header, so the next film can check it.
- **Vary the opening type across a series:** a cold open on UI, a fragment close-up, giant type, a broken world.
- So far:
  - CloudScale 2 = A
  - Slate 30s = A, with a Manifesto echo in its payoff
  - The next film should lean toward B, C, D or E unless the brief clearly calls for A.

## 6. Brief header (add to `<film>-script.md`)
```
Core idea : <one sentence>
Arc       : <shape or blend> — why this material has this shape (1 line)
Turns     : beat1 → BUT/THEREFORE → beat2 → … (one line per link)
Rhyme     : how the ending answers the opening
```
